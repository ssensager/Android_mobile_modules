# Пояснительная записка — Лабораторная работа № 5 («МедКонтроль»)

## 1. Глоссарий простыми словами

- **Room** — удобная обёртка от Google над встроенной базой SQLite в Android. Проверяет SQL-запросы ещё на этапе сборки, чтобы опечатка в названии колонки не обрушила приложение у пользователя.
- **Entity (`@Entity`)** — обычный Java-класс, который описывает одну таблицу базы данных: поля класса становятся столбцами таблицы.
- **ForeignKey (`@ForeignKey`)** — внешний ключ, то есть жёсткая ссылка из одной таблицы на строку в другой таблице (например, каждый приём ссылается на конкретный препарат).
- **CASCADE (`ForeignKey.CASCADE`)** — правило каскадного удаления: если удалить препарат, база автоматически удалит все связанные с ним приёмы, не оставляя «осиротевших» строк.
- **Index (`@ColumnInfo(index = true)`)** — быстрый указатель по столбцу внешнего ключа (как алфавитный указатель в книге), чтобы соединение таблиц не замедлялось с ростом записей.
- **DAO (`@Dao`)** — интерфейс с методами чтения и записи (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) для конкретной таблицы.
- **Relation (`@Relation` + `@Embedded`)** — способ получить препарат сразу вместе с его действующим веществом и списком всех приёмов одним согласованным запросом (`@Transaction`).
- **Repository** — слой между базой и экранами: прячет работу с DAO и отправляет все записи в фоновый пул потоков (`ExecutorService`), чтобы не зависал интерфейс.
- **WorkManager** — системный планировщик фоновых задач Android. В отличие от обычного таймера внутри процесса, его задачи сохраняются системой и срабатывают даже после закрытия приложения или перезагрузки телефона.
- **NotificationChannel** — канал уведомлений (обязателен с Android 8): позволяет пользователю в настройках системы управлять звуком и важностью напоминаний.
- **BroadcastReceiver** — системный приёмник коротких событий; здесь он принимает нажатие кнопки «Принято» прямо из шторки уведомлений и отмечает приём в базе без запуска экрана.

## 2. О чём эта лаба за 20 секунд

«МедКонтроль» — это мобильный фармацевтический трекер на Java 17 и Room. Пользователь ведёт свою аптечку препаратов, привязанных к действующим веществам, а отдельный слой бизнес-логики автоматически проверяет все сочетания по таблице правил несовместимости из базы и показывает постоянное предупреждение с градацией опасности и визуальной шкалой риска на `Canvas`. На экране препарата можно планировать надёжные напоминания через `WorkManager` и отмечать приём кнопкой «Принято» прямо из уведомления.

## 3. Что сделано по пунктам и как показать на экране

### Схема модели данных (таблицы и связи)

```text
+-----------------------------------+        1 : N (CASCADE)
|         active_substance          |-------------------------------+
+-----------------------------------+                               |
| PK  id : INTEGER (auto)           |                               |
|     name : TEXT                   |                               v
|     description : TEXT            |         +-------------------------------------+
+-----------------------------------+         |              medicine               |
         | 1                  | 1             +-------------------------------------+
         |                    |               | PK  id : INTEGER (auto)             |
         | N (CASCADE)        | N (CASCADE)   |     name : TEXT                     |
         v                    v               |     dosage : TEXT                   |
+-----------------------------------------+   | FK* substanceId -> active_substance |
|              conflict_rule              |   |     scheduleTime : TEXT             |
+-----------------------------------------+   |     notes : TEXT                    |
| PK  id : INTEGER (auto)                 |   +-------------------------------------+
| FK* substanceAId -> active_substance    |                     | 1
| FK* substanceBId -> active_substance    |                     | N (CASCADE)
|     severity : TEXT (HIGH/MEDIUM/LOW)   |                     v
|     title : TEXT                        |   +-------------------------------------+
|     recommendation : TEXT               |   |               intake                |
+-----------------------------------------+   +-------------------------------------+
                                              | PK  id : INTEGER (auto)             |
  Примечание: FK* означает внешний ключ       | FK* medicineId -> medicine          |
  с индексом @ColumnInfo(index = true)        |     scheduledAtMs : INTEGER         |
  и стратегией onDelete = CASCADE.            |     isTaken : INTEGER (boolean)     |
                                              +-------------------------------------+
```

### Что реализовано и как показать преподавателю

1. **Четыре связанные таблицы Room с внешними ключами и индексами** (`active_substance`, `medicine`, `conflict_rule`, `intake`).
   - *Как показать:* открыть приложение — при первом запуске в фоне заполняются 6 действующих веществ, 5 правил несовместимости, 3 препарата и история их приёмов. Нажать иконку книги в верхней панели («Справочник правил»), чтобы показать все правила из SQLite.
2. **Составная выборка `@Embedded` + `@Relation` + `@Transaction`** (`MedicineWithDetails`).
   - *Как показать:* на каждой карточке препарата сразу видны название, дозировка, действующее вещество из таблицы `active_substance` и счётчик «Приёмы: X из Y» из таблицы `intake`.
3. **Выделенная доменная бизнес-логика (`InteractionChecker`) + 7 модульных тестов (`Lab5UnitTest`)**.
   - *Как показать:* на главном экране сразу после запуска горит постоянная красная карточка конфликта «Нурофен (Ибупрофен) + Кардиомагнил (Аспирин)». Добавить «Цитрамон» с веществом «Кофеин» — появится конфликт среднего уровня (жёлтый) с Панадолом; добавить «Омез» с «Омепразолом» — появится конфликт низкого уровня (синий). Запустить `gradlew testDebugUnitTest` — все 7 тестов проходят.
4. **Визуальная шкала риска на `Canvas` (`RiskGaugeView`)**.
   - *Как показать:* сразу под баннером отображается цветная шкала индекса риска (`0–100`) с бегунком и счётчиками `Критичных / Средних / Низких`. При удалении или добавлении препарата шкала мгновенно перерисовывается.
5. **Безопасное удаление с подтверждением, каскадом и отменой (`Undo`) + Пустое состояние**.
   - *Как показать:* нажать корзину у препарата — диалог предупредит, сколько связанных приёмов удалится каскадно (кнопка по умолчанию — «Отмена»). После подтверждения внизу появится `Snackbar` с кнопкой «Отменить», возвращающей препарат вместе со всеми его приёмами. Если удалить все препараты — откроется понятный экран пустого состояния с кнопкой «Добавить препарат».
6. **Уведомления через `WorkManager`, обработка отказа в `POST_NOTIFICATIONS` и кнопка «Принято» из шторки**.
   - *Как показать:* открыть карточку препарата -> нажать «Тест через 5 сек» -> свернуть приложение -> через 5 секунд придёт уведомление с названием, дозировкой и веществом. Нажатие на текст открывает сразу карточку препарата; нажатие на кнопку «Принято» в самом уведомлении закрывает его и в фоне меняет статус приёма в Room на «Принято». Если отклонить разрешение на уведомления, приложение не падает — появляется аккуратная подсказка, а аптечка и проверка конфликтов продолжают работать.

## 5. Ответы на вопросы раздела 8 (обоснование выбранного подхода)

### 1. Почему модель данных разбита именно на такие таблицы? Какие альтернативы рассматривались и чем они хуже?
Модель разделена на 4 нормализованные таблицы: `active_substance`, `medicine`, `conflict_rule` и `intake`. Препарат связан с действующим веществом по `substanceId`, потому что несовместимость определяется именно химическим веществом, а не торговым названием («Нурофен» и «Миг» оба содержат Ибупрофен).
- *Альтернатива 1 (одна таблица с полем `substanceName` строкой и приёмами в JSON/строке):* приводит к опечаткам («ибупрофен» vs «Ибупрофен »), ломает поиск конфликтов и не даёт быстро обновлять статус отдельного приёма из уведомления.
- *Альтернатива 2 (связывать `conflict_rule` напрямую с `medicine`):* пришлось бы дублировать правила для каждого торгового бренда с тем же действующим веществом.

### 2. Почему для внешних ключей выбрана стратегия удаления `CASCADE`?
Для `intake.medicineId -> medicine.id` выбрано `ForeignKey.CASCADE`, потому что запись о приёме не имеет смысла без самого препарата — при удалении лекарства не должно оставаться «висячих» приёмов-сирот, искажающих историю и статистику. Для связей с `active_substance` также выбран `CASCADE`, чтобы в базе сохранялась ссылочная целостность и не возникало битых ссылок. При этом, чтобы пользователь не потерял историю приёмов случайно, перед удалением препарата показывается диалог подтверждения с числом связанных приёмов, а после удаления доступен `Snackbar` «Отменить», который транзакционно восстанавливает препарат и его приёмы. Вариант `SET NULL` здесь не подходит (приём без препарата бессмысленен), а `RESTRICT` мешал бы пользователю удалить старый препарат из аптечки, пока он вручную не удалит каждый его приём.

### 3. Почему правила предметной области хранятся данными в таблице БД, а не в коде, и как это влияет на расширение справочника?
Все правила несовместимости лежат в таблице `conflict_rule` (`substanceAId`, `substanceBId`, `severity`, `title`, `recommendation`), а класс `InteractionChecker` не содержит ни одного захардкоженного названия лекарства или ветвления `if ("Ибупрофен" ...)`. Благодаря этому расширение справочника (добавление новых веществ, правил или подгрузка обновлений с сервера) сводится к вставке строк в SQLite и не требует переписывать, перетестировать и пересобирать логику приложения.

### 4. Как визуально передаётся серьёзность проблемы и почему выбран именно такой способ?
Для каждого уровня опасности используются одновременно три независимых сигнала — **цвет**, **уникальный значок** и **явный текст** (`Высокий риск` — алый + знак стоп-опасности; `Средний риск` — янтарный + треугольник предупреждения; `Низкий риск` — синий + значок информации; `Совместим` — бирюзовый + галочка). Такой подход понятен даже людям с нарушением цветовосприятия, а визуальная градация не даёт «замылиться» вниманию: красным выделены только действительно опасные сочетания. Главное предупреждение оформлено постоянной карточкой в верхней части экрана и дополнено шкалой `RiskGaugeView`, а не исчезающим `Toast` на полсекунды, потому что незамеченный лекарственный конфликт создаёт ложное чувство безопасности.

### 5. Почему для уведомлений выбран `WorkManager` и что произойдёт при использовании обычного таймера?
`WorkManager` сохраняет запланированные задачи во внутренней базе системы и сам восстанавливает их через системные механизмы (`JobScheduler` / `BOOT_COMPLETED`). Поэтому напоминание о приёме препарата гарантированно придёт в нужное время даже после того, как пользователь смахнул приложение из списка недавних или перезагрузил телефон. Обычный `Handler.postDelayed`, `Timer` или поток живут только внутри процесса приложения: как только Android выгрузит процесс для экономии памяти или устройство перезагрузится, таймер бесследно исчезнет, и человек пропустит приём лекарства.
